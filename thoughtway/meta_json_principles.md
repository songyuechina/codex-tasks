状态：项目级规则  
建议放置：`D:/codex-tasks/thoughtway/meta_json_principles.md`

---

# 一、目标

`meta.json` 的根本目的不是重复源码，而是**压缩源码的核心信息**，使智能体能够：

1. 迅速定位并引用脚本中的关键函数  
2. 迅速理解函数与脚本的核心流程要点  
3. 摆脱源码体量过大带来的阅读负担  
4. 在整体规则指导下，迅速修改、重组或重写脚本  

---

# 二、两层结构

每个脚本应建立两份 meta：

- `quote.meta.json`：引用层信息
- `procedure.meta.json`：流程层信息

---

# 三、引用层（quote.meta.json）应写什么

引用层的任务是：

> 让智能体**迅速引用**这个脚本。

必须优先压缩以下信息：

1. **脚本角色**
   - 这个脚本在系统中是什么层
   - 它解决的核心问题是什么

2. **系统位置**
   - 它属于连接层 / 选择层 / 协调层 / 日志层 / 内容分析层 / 守护层中的哪一层
   - 它与哪些核心脚本协作

3. **核心函数 / 公共接口**
   - 只列真正重要、会被引用的函数
   - 不要平均罗列所有小函数

4. **输入输出骨架**
   - 输入大致是什么
   - 输出大致是什么
   - 是否会返回统一结构 / bool / list / context manager 等

5. **副作用与风险边界**
   - 是否会连接 CAD
   - 是否会写文件
   - 是否会启动长循环
   - 是否会抢焦点 / 关闭窗口 / 修改 logger / 修改全局状态

6. **必须保留的经验**
   - 哪些策略是经过实践验证有效的
   - 这些经验将来重写时不能丢

7. **是否允许重组**
   - 可重构 / 可瘦身 / 非必要不改 / 高价值稳定核心

---

# 四、流程层（procedure.meta.json）应写什么

流程层的任务是：

> 让智能体**迅速把握流程要点**。

必须优先压缩以下信息：

1. **适用场景**
   - 在什么情况下应调用这个脚本/函数

2. **前置条件**
   - 使用前必须满足什么条件
   - 是否要求先连接 CAD、先打开文件、先建立 logger 等

3. **核心流程骨架**
   - 只写主要步骤
   - 不要把源码逐行翻译成自然语言

4. **成功 / 失败判定**
   - 什么算调用成功
   - 什么算失败
   - 失败后按什么策略处理

5. **不可丢失的步骤**
   - 哪些流程经验是重写时不能丢的

6. **不要怎么用**
   - 明确写出误用场景
   - 说明它不该承担什么职责

7. **与其他核心脚本的关系**
   - 先调用谁
   - 依赖谁
   - 不应绕过谁

---

# 五、什么是好的 meta

好的 meta 应该做到：

- 读完后，智能体不必先读完整源码，就能知道是否应该引用这个脚本
- 读完后，智能体能知道核心函数和核心步骤
- 读完后，智能体能知道哪些经验必须继承
- 读完后，智能体能决定：复用 / 改写 / 重写

---

# 六、什么是无效的 meta

以下写法是无效或低价值的：

- 只是把源码换成自然语言
- 平均列出所有函数，不分主次
- 只讲参数，不讲角色
- 只讲流程，不讲前置条件和失败判定
- 不写风险、副作用、边界
- 不写哪些经验必须保留

---

# 七、总原则

meta.json 的根本目的，是让智能体摆脱脚本过多内容的束缚。

其中：

- **引用层** 负责压缩脚本的角色、接口、关键函数、输入输出与边界  
- **流程层** 负责压缩脚本的适用场景、前置条件、核心步骤、成功失败判定与不可丢失的经验  

---

# 八、重写原则

智能体不必机械继承历史函数形式，但必须继承：

- 项目思想
- 系统规则
- 已被实践验证有效的经验
- 案例与校验标准

因此，meta 不是为了束缚重构，而是为了支撑高质量重构。
